# Linux Network Visibility Lab

## Objective

Observe and understand real network traffic generated by my Arch Linux endpoint using Wireshark.

The goal of this lab was to connect networking theory to real packet captures and understand what information is visible at different layers of communication.

## Lab Environment

- Arch Linux
- Linux Zen kernel
- KDE Plasma
- Wireshark
- OpenSSH
- Tailscale
- Termius on iPhone
- Home Wi-Fi network

## Part 1 - ARP Resolution

While capturing traffic on the Wi-Fi interface, I observed ARP requests and replies.

Example flow:

```text
Linux Endpoint
     |
     | Who has 192.168.100.68?
     v
Local Network
     |
     | 192.168.100.68 is at
     | 42:92:fd:03:f8:90
     v
Linux Endpoint
```

ARP allows a device to determine the MAC address associated with an IPv4 address on the local network.

The relationship observed was:

```text
IPv4 Address
     |
     | ARP
     v
MAC Address
```

This demonstrated the difference between Layer 3 addressing using IP and Layer 2 delivery using MAC addresses.

## Part 2 - DNS Resolution

I then captured DNS traffic generated by the Linux endpoint.

The capture showed DNS queries and responses using UDP port 53.

The observed process was:

```text
Application
     |
     v
DNS Query
     |
     v
DNS Resolver
     |
     v
DNS Response
     |
     v
IP Address
```

The capture also demonstrated different DNS record types.

### A Record

```text
Domain Name
     |
     v
IPv4 Address
```

### AAAA Record

```text
Domain Name
     |
     v
IPv6 Address
```

### CNAME Record

```text
Domain Name
     |
     v
Alias
     |
     v
Canonical Domain
```

This helped demonstrate that DNS resolution can involve multiple records before the final destination address is returned.

## Part 3 - TCP Three-Way Handshake

Using an SSH connection from an iPhone to the Arch Linux endpoint over Tailscale, I captured the creation of a TCP session.

The capture showed:

```text
Client                         Server

SYN ------------------------->

    <---------------- SYN/ACK

ACK ------------------------->
```

This is the TCP three-way handshake.

### SYN

The client requests a new TCP connection.

### SYN/ACK

The server acknowledges the request and indicates that the server is ready to establish the connection.

### ACK

The client acknowledges the server response.

The TCP session is now established.

## Part 4 - Client and Server Ports

The SSH server listened on:

```text
TCP/22
```

The client used a temporary high-numbered port.

Example:

```text
iPhone
100.x.x.x:53986
        |
        | TCP
        v
Arch Linux
100.x.x.x:22
```

This demonstrated the difference between a well-known server port and an ephemeral client port.

## Part 5 - SSH Negotiation

Using Wireshark's Follow TCP Stream feature, I observed the beginning of the SSH session.

Before encrypted application traffic began, the endpoints exchanged SSH protocol information.

The capture included protocol identifiers similar to:

```text
SSH-2.0-libssh2
SSH-2.0-OpenSSH
```

The endpoints also negotiated cryptographic capabilities including key exchange, host key, and encryption algorithms.

Examples observed included:

```text
curve25519
ED25519
ChaCha20
AES
```

After negotiation completed, the application payload became encrypted.

## Part 6 - Encrypted Traffic

Commands entered through the SSH terminal were not visible as plaintext inside the packet capture.

Wireshark could observe metadata such as:

```text
Source IP
Destination IP
Source port
Destination port
TCP flags
Sequence numbers
Acknowledgements
Packet sizes
Timing
Connection duration
```

However, the encrypted SSH session prevented the packet capture from simply revealing:

```text
Shell commands
Passwords
Terminal output
```

This demonstrated the difference between network visibility and application-layer content protected by encryption.

## Part 7 - Network vs Endpoint Telemetry

Wireshark provided network context:

```text
IP Address
     |
     v
TCP Connection
     |
     v
Port 22
     |
     v
SSH Traffic
```

The Linux endpoint provided additional context through OpenSSH logs:

```text
Remote Address
     |
     v
sshd
     |
     v
User
     |
     v
ED25519 Public-Key Authentication
```

Combining both sources provides a more complete security picture.

```text
Network Telemetry
        +
Endpoint Telemetry
        |
        v
Security Context
```

## Security Relevance

This lab demonstrated why security investigations often require more than one telemetry source.

Network telemetry can identify:

- Who communicated
- Which protocol was used
- Which ports were involved
- When communication occurred
- How much traffic was transferred

Endpoint telemetry can add:

- Process information
- User identity
- Authentication method
- Service information
- Execution context

This relationship is important when understanding technologies such as EDR and XDR, where multiple telemetry sources can be correlated during an investigation.

## What I Learned

This lab converted several networking concepts from theory into observable behavior:

```text
ARP
IP -> MAC

DNS
Domain -> IP

TCP
SYN -> SYN/ACK -> ACK

SSH
TCP/22 -> Negotiation -> Encrypted Traffic
```

The most important lesson was that packet analysis is not only about reading individual packets.

Understanding the complete flow requires connecting:

```text
Addressing
     |
     v
Name Resolution
     |
     v
Transport
     |
     v
Encryption
     |
     v
Application Behavior
```

This provides a much clearer understanding of how endpoint and network security telemetry relate to each other.
